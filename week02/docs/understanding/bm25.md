# Step 3 — BM25

Guide to `Bm25Model` in `ranking.py`: the formula, what each parameter actually
does to a ranking, and how it compares with week01's cosine similarity.

For the Binary Independence Model, the log-odds reasoning behind IDF, and the
identity that connects the two, see
[binary-independence-model.md](binary-independence-model.md).

---

## 1. The formula

```
score(q, d) = Σ over t in q of  idf(t) · tf·(k₁+1) / (tf + k₁·K(d))

K(d) = (1 − b) + b · |d| / avgdl
idf(t) = log( 1 + (N − df + 0.5) / (df + 0.5) )
```

**Every symbol, and the line that computes it**

| Symbol | Meaning | Computed by | Line |
|---|---|---|---|
| `tf` | occurrences of *t* in *d* | `term_frequency_in()` | `ranking.py:333` |
| `k₁+1` | the saturation constant | `self.k1 + 1.0` | `ranking.py:308` |
| `K(d)` | length norm | `length_norm()` | `ranking.py:308` |
| saturation | `tf(k₁+1)/(tf + k₁·K(d))` | `saturation()` | `ranking.py:308` |
| `idf(t)` | log-odds weight | `idf_for(term)` | `ranking.py:336` |
| contribution | `idf × sat` | `contribution = idf * sat` | `ranking.py:338` |
| **the sum** | | `total += contribution` | `ranking.py:339` |
| drop zero scores | a paper sharing no term is not returned | `if score <= 0.0` | `ranking.py:377` |
| sort best first | `key=(-score, doc_id)` | `_rank()` | `ranking.py:377` |

`tf·(k₁+1)/(tf + k₁·K(d))` is a single line of arithmetic, `ranking.py:308`.
Everything else in the model is bookkeeping.

## 2. k₁ — the saturation parameter

**What it controls:** how fast an extra occurrence stops helping.

Measured on a paper of average length (171.7 terms):

| tf | k₁ = 0 | k₁ = 0.2 | k₁ = 0.6 | **k₁ = 1.2** | k₁ = 2 | k₁ = 8 |
|---|---|---|---|---|---|---|
| 1 | 1.0000 | 1.0005 | 1.0011 | **1.0017** | 1.0020 | 1.0027 |
| 2 | 1.0000 | 1.0912 | 1.2316 | **1.3766** | 1.5023 | 1.8044 |
| 3 | 1.0000 | 1.1252 | 1.3340 | **1.5728** | 1.8022 | 2.4600 |
| 5 | 1.0000 | 1.1540 | 1.4290 | **1.7752** | 2.1447 | 3.4681 |
| 10 | 1.0000 | 1.1765 | 1.5097 | **1.9649** | 2.5013 | 5.0068 |
| 20 | 1.0000 | 1.1882 | 1.5535 | **2.0758** | 2.7280 | 6.4342 |

Read the k₁ = 0 column: **every value is exactly 1.0000**. That is the binary
indicator, and it is why k₁ = 0 reproduces the Binary Independence Model
exactly — see the [BIM guide](binary-independence-model.md) §5 for that identity
and the measurement that proves it.

Read the k₁ = 1.2 column: tf = 10 is worth **1.96×** tf = 1, not 10×.

Read **down** any column and the shape never changes: large gains early,
diminishing returns forever after. That is what "saturation" means.

**Where the default comes from.** 1.2 is the literature default. This week's
evaluation shows the ranking is completely flat either side of it:

| k₁ | MRR | MAP | P@1 | queries with no hit |
|---|---|---|---|---|
| **0** | **0.917** | **0.875** | **0.833** | 0 |
| 0.6 | 1.000 | 0.925 | 1.000 | 0 |
| **1.2** | **1.000** | **0.925** | **1.000** | 0 |
| 2 | 1.000 | 0.925 | 1.000 | 0 |
| 8 | 1.000 | 0.925 | 1.000 | 0 |

Every k₁ above zero gives **identical** results on these 12 queries. The
parameter matters far less than whether saturation is applied *at all*: setting
it to zero costs 0.083 MRR, moving it from 0.6 to 8 costs nothing.

That flatness is a property of a small corpus with single-topic queries, not a
general truth about BM25. It does mean the default could not be defended from
this evaluation — it is defended from the literature, and reported as such.

## 3. b — the length normalisation parameter

**What it controls:** how much a long paper is penalised.

```python
# ranking.py:308
return (1.0 - self.b) + self.b * (length / self.average_document_length)
```

| \|d\| | b = 0 | b = 0.75 | b = 1 |
|---|---|---|---|
| 144 | **1.0000** | 0.8790 | 0.8387 |
| 171 | **1.0000** | 0.9969 | 0.9959 |
| 197 | **1.0000** | 1.1105 | 1.1474 |

At **b = 0 every K(d) is exactly 1.0000**. Length is not merely down-weighted at
b = 0, it is *gone* from the formula. `tests/test_ranking.py` asserts that, and
the Streamlit slider sets it live.

Sweeping it over the 12 judged queries:

| b | MRR | MAP | P@1 |
|---|---|---|---|
| **0** | **0.958** | **0.883** | **0.917** |
| 0.5 | 1.000 | 0.925 | 1.000 |
| **0.75** | **1.000** | **0.925** | **1.000** |
| 1.0 | 1.000 | 0.925 | 1.000 |

**The honest limitation.** This corpus runs 144–197 terms — a ratio of 1.37× —
so the length effect is real but mild. Removing length altogether (b = 0) costs
0.042 MRR, and the difference comes from **exactly one query out of twelve**:

```
q12  "metadata structured field search"     relevant: p19
      b = 0.00   ranking  p15, p19, p18 …   → p19 at rank 2   MRR 0.500
      b = 0.75   ranking  p19, p15, p18 …   → p19 at rank 1   MRR 1.000
```

At b = 0, p15's longer body outscores p19's on raw term mass even though p19 is
*about* structured field search. Length normalisation is what fixes it. One query
in twelve is a thin result: on a corpus of mixed article lengths, where one paper
is forty times another, b would matter far more.

Saying "b = 0.75 is correct" is not supportable from this corpus. Saying "b = 0.75
is the standard default, and this corpus is too uniform to demonstrate its value
beyond a single query" is.

## 4. A whole score, arithmetic shown

Query `structured field search`, paper **p19**, k₁ = 1.2, b = 0.75.

```
query terms after preprocessing:  'structur field', 'search'
|p19| = 161        avgdl = 171.7
K(d)  = (1 − 0.75) + 0.75 × 161/171.7
      = 0.25 + 0.70331
      = 0.953262
```

| term | tf | idf | saturation | = idf × sat |
|---|---|---|---|---|
| `structur field` | 1 | 2.6391 | 1.0262 | 2.7081 |
| `search` | 2 | 1.1727 | 1.3995 | 1.6413 |

```
score(p19) = 2.7081 + 1.6413 = 4.3494
```

Note the phrase: three query words, **two** terms. "structured field" is a single
index entry, so it is counted once. Preprocessing and ranking are separate
stages, and the phrase list is what connects them.

**Verify it yourself**

```powershell
python ranking.py
```

## 5. BM25 against week01's cosine

week01 ranked by cosine similarity over TF-IDF vectors:

```
cos(q, d) = (q · d) / (‖q‖ × ‖d‖)
```

Three differences, all of which matter:

| | week01 cosine | BM25 |
|---|---|---|
| term frequency | **unused** — a term is present or absent | saturated by k₁ |
| length | divided out entirely by ‖d‖ | partially, by K(d) |
| the |a| it's used on | a whole paper | a **field**, or a **region** |

Measured on the 12 judged queries in step 7:

| model | P@1 | P@5 | R@10 | MRR | MAP |
|---|---|---|---|---|---|
| tfidf cosine (week01) | 0.917 | **0.617** | 0.958 | 0.958 | 0.883 |
| BIM | 0.833 | 0.633 | 0.958 | 0.917 | 0.875 |
| **BM25** | **1.000** | 0.617 | 0.958 | **1.000** | **0.925** |

BM25 gets the right paper first on every query. But look at P@5: it is **the
same as cosine's**, and lower than BIM's. BM25 is better at the *top* and no
better in the tail, which is exactly what you would expect from a model whose
gains come from repeated terms — a paper that repeats a term fifteen times will
rise, and nothing here is pushing irrelevant papers down.

Reporting only MRR would hide that. `evaluation.md` explains why both are
measured.

## 6. Reading the parameters in the interface

The Streamlit app exposes k₁ and b as sliders (`app.py`, the Search tab):

- move **k₁ to 0** and the app says *"this **is** the Binary Independence
  Model"*. It is not a caption; `tests/test_ranking.py::TestTheBridge` asserts
  the scores are identical to floating point.
- move **b to 0** and length stops affecting anything.
- the formula is printed under the sliders, with the live values substituted.

The console does the same with `bm25:` / `bim:` prefixes:

```powershell
python main.py --console bm25: "term weighting saturation"
python main.py --console bim: "term weighting saturation"
```

## 7. What this step deliberately does **not** do

- **It does not tune.** k₁ and b are literature defaults, exposed rather than
  fitted. Fitting them against 12 judged queries and then reporting the result on
  those same 12 queries would be circular.
- **It does not return regions.** BM25 ranks a whole paper. A paper can score
  highly because one term appears in its title and another in a buried
  paragraph, and the model cannot tell you that. Steps 5 and 6 exist for exactly
  this gap.
- **It does not handle fields.** Step 4.
- **It does not claim to be better than cosine in general.** It is better on
  these 12 queries, on this 20-paper corpus, and that is the entire claim.
